# tts-on-aws

AWS Lambda container for text-to-speech. CosyVoice3 running on ONNX Runtime, CPU only, no GPU and no SageMaker endpoint: batch synthesis with zero-shot voice cloning from a short reference clip, per-clip ASR-roundtrip QC, and a DynamoDB voice catalog with a live user-registration path.

Two state machines share one container image and one dispatcher: **synthesis** ([definitions.json](definitions.json)) and **register-voice** ([definitions_register_voice.json](definitions_register_voice.json)).

This README is the single developer doc for the workflow. The numbered **[Design record](#design-record)** at the bottom preserves the design decisions and measurements the code cites (`§6`, `§7a`, `§10` references in docstrings and comments point there).

## Model Stack

| Model | Format | Purpose |
|-------|--------|---------|
| CosyVoice3 LLM (Qwen2 backbone) | ONNX **INT4** | text → speech tokens |
| CosyVoice3 Flow (matcha CFM estimator) | ONNX **FP32** | speech tokens → mel |
| CosyVoice3 HiFT | ONNX | mel → 24 kHz waveform |
| CosyVoice3 speech tokenizer | ONNX | reference audio → speech tokens (registration) |
| CAMPPlus | ONNX | 192-dim speaker embedding (registration) |
| faster-whisper **base** (multilingual) | CTranslate2 INT8 | ASR-roundtrip QC + register-time transcript check |

INT4 for the LLM is not merely a size choice — it beat FP16 on a live listening comparison as well as being ~3x faster (§9). The Flow estimator stays FP32: INT8 failed the listening gate and FP16 measured *slower* on CPU (§3).

All six archives are seeded to `s3://{ProxyBucket}/_model_artefacts/` by the CodeBuild `BuildAndSeedModels` custom resource at stack creation. There is **no CloudFront fallback in use** — every model is a fixed known artefact and `CLOUDFRONT_URL` is never set. ([lib/model_store.py](lib/model_store.py) still carries the fallback code, inherited from speech-diarization-on-aws.)

## Workflow States

Entry point for every state: [lambda_function.py](lambda_function.py) dispatches on the `operation` field.

**Synthesis** — `Check and preprocess` → `Map batch synthesis` (INLINE ItemProcessor, `MaxConcurrency: 40`) → `Usage tracking`. Inside the Map, per iterator: `Synthesize LLM` → `Synthesize Flow+HiFT` → `Verify output`.

**One caller batch becomes up to 40 iterators, split by estimated work** — see Gotchas. It was originally one iterator per batch, which meant a Map running at concurrency 1.

| State | `operation` | Tier | What it does |
|-------|-------------|------|--------------|
| Check and preprocess | `StateCheckAndPreprocess` | 1-core | validate request, split `batches` → up to 40 work-balanced `data.iterators` |
| Synthesize LLM | `StateSynthesizeLLM` | 2-cores | text → speech tokens, per-batch Python loop |
| Synthesize Flow+HiFT | `StateSynthesizeFlowHift` | 4-cores | tokens → mel → 24 kHz WAV → S3 |
| Verify output | `StateVerifyOutput` | 1-core | ASR roundtrip QC, best-of-N selection |
| Usage tracking | `StateUsageTracking` | half-core | per-state cost from execution history |

**Register-voice** — `Validate reference` → `Extract conditioning` (Parallel, 3 branches) → `Write voice record`.

| State | `operation` | Tier | What it does |
|-------|-------------|------|--------------|
| Validate reference | `StateValidateReference` | 1-core | WAV format check + ASR transcript match (rejects a mismatch) |
| Extract speech tokens | `StateExtractSpeechToken` | 2-cores | reference → speech tokens |
| Extract spk embedding | `StateExtractSpkEmbedding` | half-core | CAMPPlus 192-dim |
| Extract speech feat | `StateExtractSpeechFeat` | half-core | matcha mel (pure DSP, no model) |
| Write voice record | `StateWriteVoiceRecord` | half-core | conditioning npz + preview/source to S3, DDB record |

There is no `StateLoadVoiceConditioning`: the ~1 MB conditioning blob cannot travel through a state payload, so a loader state could only pass a pointer. Both synthesis states call `get_conditioning()` directly instead — see [lib/conditioning_cache.py](lib/conditioning_cache.py).

## Lambda Memory Tiers

**Seven tiers declared, four routed to.** One container image, `!FindInMap [Lambda, <Tier>, Memory]` in [cfnstack.yaml](cfnstack.yaml). All arm64, `Timeout: 900`, `EphemeralStorage` 4096 MB at half/1-core and 6144 MB from 2-cores up.

| Tier | Memory | vCPU | Routed to | Measured peak |
|------|--------|------|-----------|---------------|
| HalfCore | 896 | <1 | yes | usage tracking 94 MB |
| OneCore | 1792 | 1 | yes | preprocess 86 MB, QC whisper 704 MB |
| TwoCores | 3584 | 2 | yes | LLM INT4 2873–2938 MB, speech-tokenizer 3179 MB |
| ThreeCores | 5376 | 3 | — | (see below) |
| FourCores | 7168 | 4 | yes | Flow+HiFT 4998 MB |
| FiveCores | 8960 | 5 | — | |
| SixCores | 10240 | 6 | — | |

Flow+HiFT is on 7168 MB rather than the 5376 MB tier that would also fit: 5376 was tight at a 5029 MB peak, and 3→4 vCPU cut cold synthesis ~43 % for ~14 % more cost (§9).

**Declaring a tier no state routes to is deliberate** — it is what lets a state be re-pointed at another tier during testing without a template change, which is why the sibling workflows do it too (measured: the siblings each route to only 3–5 of their 7 declared tiers). This stack previously carried the opposite rule — "a tier that no state routes to must be deleted" — and shipped only the four routed tiers; that rule is **withdrawn**, do not re-apply it. Each unrouted tier costs a Function + a LogGroup + an `InvokeFunction` grant at deploy time and nothing at runtime, because an unrouted function is never invoked.

Three tests pin the set: `test_all_seven_memory_tiers_are_declared_and_granted` (the exact seven, each granted `lambda:InvokeFunction` — an ungranted tier fails the execution the moment someone re-points a state at it), `test_every_referenced_lambda_tier_exists` (a one-way subset check, so declared-but-unrouted is legal), and `test_the_seven_memory_sizes_match_the_sibling_workflows` (the memory/name pairs — a swap is only comparable if `3-cores` means 5376 MB here as it does everywhere else).

## Key Conventions

- **S3 layout** — outputs `micro-workflow/tts-on-aws/output/{uuid}/`, voices `micro-workflow/tts-on-aws/voices/{voice_id}/`. Both prefixes are **hardcoded in the states**, not derived from `TARGET_NAME` like sibling stacks.
- **Checkpoint/resume** — all three synthesis states check `context.get_remaining_time_in_millis()` before each transcript and, under `REMAINING_TIME_BUFFER_MS` (60 s), persist progress to `{out_prefix}/ephemeral/` and raise `LambdaResourceTimeoutException`, which the ASL `Retry` re-invokes. Granularity is **per transcript, not mid-generation** — one pathological near-`MAX_TEXT_CHARS` transcript can still exceed the budget on its own (§10).
- **Per-item isolation everywhere** — a failing transcript records `{"error": ...}` and the loop continues; only a batch where *everything* failed raises. Same for individual best-of-N candidates, and for QC (a QC pass that cannot run records `{"passed": None, "similarity": -1.0, "error": ...}`). `Verify output` has no `States.TaskFailed` retry, so an exception escaping it discards audio that is already durably in S3.
- **Best-of-N** — `candidates` is *always* a list so Flow/HiFT and QC have one code path per tier. Length 1 for no style and pace styles, 3 for emotion styles ([lib/style_hints.py](lib/style_hints.py): `CANDIDATE_SEEDS = (1, 42, 99)`, verified clean across the full template sweep). `Verify output` picks the highest-similarity candidate, collapses the entry to a flat shape, and **deletes the losers' WAVs**. An explicit caller `seed` always forces single-shot, whatever the style.
- **Style hints are English-only** — `STYLE_VERIFIED_LANGUAGES = frozenset({"en"})` in [states/check_and_preprocess/lambda_function.py](states/check_and_preprocess/lambda_function.py). A live multilingual test measured German/Spanish QC similarity dropping from ~0.95–1.0 to 0.44–0.67 under `style` (§7a). The gate rejects the request rather than shipping degraded audio.
- **Duration control is bounded at ±10 %** — [lib/duration.py](lib/duration.py) raises `DurationOutOfRangeError` past that instead of stretching further, and is a **no-op inside ±0.5 %** (so `stretched` must be derived from the sample count, never from "a target was requested").
- **Language is stored normalized** — `qc.normalize_language()` maps the caller's free-form string to a faster-whisper code before it is persisted, because the field is later compared for *equality* (`== "en"` style gate, catalog filter) and handed to whisper. Unrecognized values degrade to auto-detect.
- **ORT session eviction across states** — `_last_operation` in [lambda_function.py](lambda_function.py) drops all cached sessions when a warm container is reused for a *different* operation. Added after a live 3.1 GB leftover-session OOM.
- **`intra_op_num_threads` is always explicit** — see Gotchas.

## Input Schema

Synthesis:

```json
{
  "uuid": "...",
  "input": {
    "batches": [{"voice_id": "...",
                 "transcripts": [{"text": "...", "target_duration_s": null}]}],
    "out_bucket": "...",   // optional, defaults to PROXY_BUCKET
    "out_prefix": "...",   // optional, derived from uuid
    "config": {"flow_steps": 6, "sampling_k": 25, "seed": null, "style": null}
  }
}
```

`MAX_TRANSCRIPTS_PER_BATCH = 100` is a coarse cap; the real bound is the payload estimate (see Gotchas). `MAX_TEXT_CHARS = 1000`. `style` must be a name in `lib.style_hints.ALL_STYLES` or absent.

Register-voice: `input.ref_bucket` / `ref_key` / `ref_transcript` plus an optional `voice` metadata dict (`name`, `gender`, `language`, `catalog`, `origin`, `license`, `comment`). `ref_transcript` is mandatory — it is fed to the model as ground truth, and a mismatch against ASR is rejected at `DEFAULT_REGISTER_THRESHOLD = 0.70`.

## AgentCore Gateway Tool

[gateway_tool/lambda_function.py](gateway_tool/lambda_function.py), target name `text-to-speech` in [../media-toolkit-gateway/cfnstack.yaml](../media-toolkit-gateway/cfnstack.yaml). Six tools: `synthesize_speech`, `register_voice`, `get_job_status`, `list_voice_collection`, `get_voice`, `describe_tool`.

- The zip is **`gateway_tool/*.py` plus `output_contract.json` — no `lib/`**. All business-rule validation that needs `lib` (style names, language gate) happens in `StateCheckAndPreprocess`, which has it.
- The same zip also serves the `ProxyBucketValidatorFunction` custom resource (`Handler: bucket_validator.handler`), so it must stay flat (`zip -j`). [gateway_tool/bucket_validator.py](gateway_tool/bucket_validator.py) is **byte-identical across all six workflows** that declare a validator; the flat zip is why it is copied rather than imported, and `micro-workflow-bundle/test/test_units.py::TestBucketValidatorParity` is what keeps the copies honest. This file was the *source* of the shared version — its guarded-read fix was backported to the five siblings, which were still hanging stacks for an hour on Delete.
- Error shape is fixed across all sibling gateway tools: `{"error": True, "errorCode": ..., "message": ...}` — `error` is a **boolean**, matching the `OutputSchema` blocks in media-toolkit-gateway. Always logged too.
- `workflow_id = uuid5(canonical JSON of the SFN input + optional idempotency token + TOOL_VERSION)` — a colliding execution name means a duplicate `StartExecution` is **absorbed** into the existing run instead of paying twice. A submit returns a **HANDLE, never results**: `{"job_id", "workflow_id", "status"}`, plus `message` when absorbed (the only signal the call did not resubmit — the `job_id` is a hash of the same input either way) and `error` when the existing run ended terminally. `status` is the existing run's, so it may be `SUCCEEDED`, and that still carries no clips: results come from `get_job_status` alone, which is what makes the declared `OutputSchema` equal to the reachable field set. Unlike the siblings there is no `current_state` on any submit branch, and no `asset_s3uri` — `_start_execution` is shared by `synthesize_speech` and `register_voice` across two state machines and has no asset of its own to echo. **`output_s3_prefix` IS on every `synthesize_speech` submit branch** (a pointer, not a result: it names where the callback waker persists `outputs.json`, and it doubles as audio-description's mechanical pre-callback deployment probe); `register_voice` still carries none — a voice registration has no output prefix, and echoing the synthesis convention there would point at a location nothing writes. (The earlier `{"status": "ALREADY_RUNNING"}` answer and the brief full-results-on-submit behavior are both retired — see §11.)
- **The two tools dedup differently, deliberately** (§11). `synthesize_speech` takes an optional `idempotency_token` — the caller's "this is the same request" assertion, never an asset id: absent, the gateway generates one, so every call gets a fresh run; supplied, the token folds into the hash and the retry is absorbed. `register_voice` takes no token at all and keeps pure parameter-hash dedup.
- **The retired `uuid` parameter is *rejected* on submit and *accepted with a log warning* everywhere else.** On `synthesize_speech` / `register_voice` a stray `uuid` is `INVALID_PARAMETER`: it used to mean two things at once, so a caller still sending it cannot be assumed to mean the surviving half, and guessing wrong means either paying twice or handing back the wrong audio. On `get_job_status` and `describe_tool` neither `uuid` nor `idempotency_token` could change the answer, so the request succeeds and the gateway logs a warning — a poll must never be lost to a hallucinated parameter mid-job.
- **Returns `workflow_id` (the service's name for the run) and `job_id`, and no `uuid` — deliberately.** The SFN input still carries a `uuid` key, set to the `workflow_id`, because every state derives its output prefix from it; that is *this execution's* local id, not the caller's token, and no response echoes the token back.
- `TARGET_NAME` is set on the function for cross-stack consistency but is **not read** (this stack's prefixes are hardcoded).
- **`describe_tool`** returns `{"version", "push_completion", "state_machine_arns", "description", "output_contract"}` — `push_completion: true` is the mechanical capability flag a callback consumer probes before any spend (audio-description's ValidateAndPlan does; a deployment without it would silently ignore `callback_task_token`); `state_machine_arns` is a **list of two** (`synthesis`, `register_voice`) because this target is backed by two state machines, unlike the siblings' single `state_machine_arn`. `output_contract` is the parsed [gateway_tool/output_contract.json](gateway_tool/output_contract.json), static per `TOOL_VERSION` — the file ships in the gateway zip (`build-deploy-s3-dist.sh` pins the member), so version and contract cannot drift. Because this target has **no labeled file outputs**, the contract documents the **inline result shapes** instead (kind `inline`): the per-clip `outputs[]` entry (success vs failure shape), `batch_qc_summary`, and the register_voice `voice` record — plus the one real file, `usage_tracking.json` (kind `file`, reached via `usage_uri`). There is consequently **no `desc` join** into `get_job_status` here; `describe_tool` is the contract's only surface. Anything not listed (`ephemeral/` checkpoints, voice conditioning internals under `voices/`) is internal and may change without notice.
- **`outputs[]` diverges from the siblings' `{uri, mime, label}` triple on purpose.** Their `label` is a **role** vocabulary (one entry per KIND of file: transcript, caption, manifest, usage), which is what makes "select by label, never parse filenames" meaningful; this target's outputs are N instances of ONE role (clip 0..N-1) carrying per-clip `duration_s`/`stretched`/`qc_passed`/`qc_similarity`/`error` that a triple cannot hold, keyed by `transcript_index` — the join key back to the caller's input array, which no sibling needs because no sibling takes an input array. Conforming would mean a vacuous repeated `label: "clip"` or losing that metadata. **speech-diarization already settled this pattern**: its per-speaker WAVs are deliberately not enumerated (non-contiguous speaker ids) — one `speakers/` prefix entry plus a manifest — so prefix-plus-manifest is the house answer for N-of-a-kind files, and this `outputs[]` is that manifest inlined. Do not "fix" the shape. The poll additionally carries `workflow_id` (recovered from the execution name, which *is* the workflow_id — an agent holding only a `job_id` could not otherwise name the run), `output_s3_prefix` (first-non-empty across iterators, not last — a later batch that failed before recording it must not blank out an established location), `usage_uri` (the advertised location of `usage_tracking.json`; siblings use `outputs[label=usage]`, which has no analogue here), and a resolved `preview_uri` on the `register_voice` poll instead of the raw `s3_preview_key`. Regression: `test/test_units.py::TestGatewayTool` (mutation-verified), plus live assertions in `media-toolkit-gateway/scripts/test_gateway.py::verify_tts_result` including that every clip uri sits under the advertised prefix.

Agent system prompt: [../media-toolkit-gateway/prompts/tts_agent.md](../media-toolkit-gateway/prompts/tts_agent.md). It is one of the two prompts that deliberately does **not** describe the siblings' shared `outputs[]` contract — there is no label vocabulary here, so an agent carrying that assumption hunts for a `label` that does not exist. The three things it exists to carry, none of which the CFN `SchemaDefinition` can express: batch size is bounded by the **payload estimate, not `MAX_TRANSCRIPTS_PER_BATCH`** (the four-row table plus the ~41-char crossover where the per-batch bound overtakes the Map-aggregate one); `target_durations_s` **must not** be derived from a diarized speaker's real timings, because the ±10 % bound turns good clips into failed entries; and a QC failure is a **review pointer, not an error**, so the correct response to `all_passed: false` is never to re-synthesize the batch. Keep it in sync with the two payload estimators and `lib/style_hints.ALL_STYLES` — the style names are quoted there verbatim and an unknown name fails the job, not the submit.

## Build & Deploy

```bash
cd tts-on-aws
bash ./build-deploy-s3-dist.sh --bucket <BASENAME> --version <VERSION> [--single-region]
```

Artefacts land under `KEY_PREFIX = {solution}/{version}/tts`, and the template is `tts-stack.template` — `TEMPLATE_NAME` is derived as `${WORKFLOW_NAME}-stack.template` like every sibling stack. It was once hardcoded `tts-on-aws-stack.template`, so that older key still exists in S3 and any stack last updated at that version still resolves against it.

`.version` gates CFN change detection — **bump it before every deploy**: CloudFormation notices a changed S3 *key*, never changed S3 *content*.

The format is **date-style `alpha.YYYYMMDD[a-z]` or `alpha.MMDD[a-z]`** — both widths are accepted and both are in circulation; prefer the 8-digit form for new stamps (`alpha.MMDD` does not order across a year boundary). Every sibling workflow and the bundle follow it — this stack's format was adopted as the house convention rather than being conformed away. The value is simultaneously an S3 key segment and the ECR `ImageTag`, so what it has to answer is "which build is this?"; a date answers directly, whereas matching a deployed semver tag back to a build meant reading git log. Semver also implied a compatibility contract these stacks never made, and since the children were bumped independently the numbers were never comparable across them. `micro-workflow-bundle/test/test_units.py::test_every_version_is_date_style` pins it, because the regression is silent: a child bumped back to a semver tag still builds and still deploys.

Note `--version` on the command line overrides the `.version` file.

## Gotchas

- **The 256 KiB Step Functions payload limit is the real batch bound, not `MAX_TRANSCRIPTS_PER_BATCH`.** The LLM→Flow handoff carries every transcript's token array for *every* candidate. Measured against real `json.dumps` envelopes, 100 transcripts fits only around 230-char texts at best-of-1 (already 257 KiB); the limit is ~24 at `MAX_TEXT_CHARS`, and ~36/~8 at emotion-tier best-of-3. `StateCheckAndPreprocess` estimates the bytes up front (`estimate_batch_payload_bytes`) and rejects the request there. **Separately**, the Map's aggregate `ResultPath` is bounded *across* batches — it is the sum over every transcript in the request, so splitting into more iterators cannot relieve it and individually-legal batches can still blow the limit together: `estimate_map_aggregate_bytes` gates that. Each text used to appear **3×** in that aggregate (`transcripts[].text`, `qc.expected`, `qc.transcribed`), 15.9× more than the information required, capping a request at 63 transcripts at `MAX_TEXT_CHARS`. `verify_output._prune_qc_evidence` now drops `qc.expected` outright, drops `qc.transcribed` on *passing* clips only (it is the sole non-derivable field and the review pointer for a failure), and pops `item["transcripts"]` after the QC loop — so `TEXT_COPIES_IN_AGGREGATE` is **1**, the worst case being an all-fail run. Ceilings went 515/215/**63** → 374/263/**118** at 42/230/1000 chars. Change what either payload carries and you must re-check both estimators; re-adding a text copy fails long-text requests at a gate that used to pass them, silently. **The aggregate estimate has three terms and two of them were independently miscalibrated in ways that nearly cancelled** — measured against a live execution it came out **1.1 % LOW**, the unsafe direction, which pays for a whole synthesis and then dies on `States.DataLimitExceeded`. `BYTES_PER_ITERATOR_ENVELOPE` was 380 from a hand-built envelope that omitted the `voice` record, the largest member because it carries `ref_transcript` **verbatim and unbounded** (`register_voice` bounds nothing); real figure 751, now **1100** for headroom over the catalog's longest `ref_transcript`. `BYTES_PER_OUTPUT_OVERHEAD` ran ~96 bytes high per entry, and on the reference run's shape the two errors annihilated. Both are now pinned separately by tests, the gate passes the **real** iterator count instead of assuming 40 (a 3-transcript request was paying for 40 envelopes), and the unit fixture includes `voice`. Two wrong terms that sum right are not calibrated, and only serializing a real execution's output found it — see §13c.
- **Map iterators are split by estimated WORK, not by transcript count, and `MAP_MAX_CONCURRENCY` must equal the ASL `MaxConcurrency`.** A reference run of 73 short clips took **52 min at Map concurrency 1**: the gateway always submits exactly one caller batch (`gateway_tool` builds a single-element `batches`), `check_and_preprocess` emitted one iterator per batch, and the other Map slots idled while three `LambdaResourceTimeoutException` checkpoint cycles each burned a full 900 s invocation for ~110–230 s of forward progress. `split_into_iterator_groups` now cuts one batch into up to `MAP_MAX_CONCURRENCY = 40` contiguous runs; the same workload re-ran in ~3 minutes with zero checkpoint resumes (§13c). Four things to know before touching it. **(1) The two concurrency numbers are one number in two files** — set the ASL lower and the surplus iterators queue into a second serial wave that re-pays every cold model load (48.8 s LLM + 35.3 s Flow + 9.4 s QC *per invocation*), which is why 13 iterators against `MaxConcurrency: 10` models *slower* than 10 iterators; set it higher and slots idle. `test_map_max_concurrency_equals_the_asl_max_concurrency` pins it in **both** `definitions.json` and `cfnstack.yaml`. **(2) Chars, not words, and not count.** Fitted on the reference run's per-transcript CloudWatch lines: LLM `4.81 + 0.1815/char`, Flow+HiFT `18.61 + 0.1819/char` (63 % of compute), QC `0.0648/char` — replaying the run from these lands within 0.2 % of the measured total. Chars are a **proxy**: speech tokens fit far better (R² 0.98 vs 0.87 for chars, 0.83 for words) but do not exist until the LLM has decoded, so they cannot schedule anything. Words are the *worst* of the three — a 12-char word costs more than a 3-char one and word count discards exactly that. Splitting by count instead costs 3.7× on a bimodal batch (60 short + 13 long). **(3) It minimizes the HEAVIEST group by bisecting on that value, and the intuitive alternative is wrong at the tail.** Every iterator runs concurrently, so the Map costs what its slowest iterator costs and a short final group is free. Filling each group to a running `total/slots` target strands the accumulated shortfall in the last group — measured a 2.2× straggler — and re-deriving the target after each cut does not fix it because the binding constraint is the final cut being refused. The bisection is optimal on 7 of 9 modelled workloads and within 1.15× of the floor on the rest. **(4) Order is a correctness requirement.** LPT bin-packing balances 1–6 % better and is unusable: `outputs` is built by positional `append` and the gateway derives the caller-facing `transcript_index` from a running counter over the iterators in order, so a reorder hands clip 40's audio back as clip 3 with nothing raising. `batch_index` counts **iterators, not caller batches**, because `wav_key` is `{out_prefix}/{job_id}_{batch_index}_{i}_c{ci}.wav` and the checkpoint key is `out_prefix + state_name + job_id + batch_index` — two iterators sharing one would overwrite each other's audio *and* resume from each other's checkpoints. Regression: `test/test_units.py::TestIteratorScheduling` (mutation-verified). **The per-batch payload gate is now deliberately conservative** and was left strict: it bounds the LLM→Flow handoff, which is really per *iterator*, so a batch it rejects would in fact have fitted once split — loosening it is a capability change. `estimate_map_aggregate_bytes` is unaffected, being cross-batch either way.
- **`intra_op_num_threads` must be set explicitly.** `patch.txt` advertises 6 CPUs (`0-5`) so ORT's cpuinfo probe doesn't abort, which makes ORT default to 6 threads even on a 1-vCPU function. Measured on the Flow estimator with 3 real CPUs: 7.33 s/call default vs 2.46 s/call at 3 threads — a **3× penalty** (the `pthread_setaffinity_np` noise in every Lambda log was this). [lib/sessions.py](lib/sessions.py) derives it from `AWS_LAMBDA_FUNCTION_MEMORY_SIZE`. The estimator stops scaling past ~4 vCPU, so tiers are chosen by RAM, not threads.
- **`ensure_cpuinfo_files()` is a call, not an import side effect.** Importing `lib.ort_init` does nothing on its own; `lib/sessions.py` invokes it explicitly before `import onnxruntime`. A missing `/sys/devices/system/cpu/possible` makes ORT `terminate()` on arm64 with "Attempt to use DefaultLogger but none has been registered" — unrecoverable and nearly undiagnosable, so don't remove either the call or `patch.txt`.
- **onnxruntime is pinned to 1.18.0** for the whole container. Newer ORT hard-crashes the community FP16 LLM graphs at session-init (SimplifiedLayerNorm fusion bug, reproduced on a recent release); every model here was verified to load *and* run under 1.18.0.
- **faster-whisper is `base`, not `base.en`.** A one-word slip silently breaks all non-English QC without raising.
- **faster-whisper rejects anything outside its 100-code language tuple** with a raw `ValueError` — hence `qc.normalize_language()`. The gateway's `register_voice` InputSchema declares `language` as free-form prose because CFN `SchemaDefinition` has no `enum`, so an agent *will* send "English".
- **`catalog` is a DynamoDB reserved keyword** — every `KeyConditionExpression` touching it must alias (`#c = :c` + `ExpressionAttributeNames`). Both [lib/voice_store.py](lib/voice_store.py) and the gateway do.
- **Both state machines are defined twice.** `cfnstack.yaml` inlines them as `DefinitionString: !Sub |-`; `definitions*.json` are the editable source of truth and ship only inside `source_code.zip`. Nothing in the build enforces agreement — the parity test in `test/test_units.py` does, so run the suite after editing either copy.
- **`ref_s3uri` must be in the proxy bucket.** `TtsLambdaRole` grants `s3:GetObject` on `${ProxyBucket}/*` only; the gateway rejects other buckets at submit time so the agent doesn't get a `job_id` that dies on `AccessDenied` a minute later.
- **QC never fails the workflow** — a `SUCCEEDED` execution says nothing about content quality. The retry-with-new-seed policy is an open decision (§10) awaiting real fail-rate data. `get_job_status` surfaces `batch_qc_summary` prominently but does not gate on it.
- **`usage_tracking.json` once billed a timed-out invocation 0 s.** The duration list dropped any invocation with `succeeded_ts is None`, so a `TaskFailed` — a Lambda killed at its 900 s timeout, the single most expensive invocation possible — contributed 0 s while `invocations` stayed correct, making the output internally inconsistent in a way that read as precise. Checkpoint/resume makes a timeout the NORMAL path at real batch sizes (§10), so it fired on ordinary runs and under-reported real runs severalfold. This stack was the reference implementation for the fix; the sibling workflows were ported from it. **Two invariants to preserve when touching this file:** `_billed_sec` falls back to `failed_ts`, and 0.0 is correct **only** when an attempt has NO terminal event at all (this state's own in-flight record) — that case is what `incomplete` now means. `wall_sec` sums attempts per `entered_id` *before* taking the max across occurrences, because every retry attempt chains back to the same `TaskStateEntered` while concurrent Map iterators each get their own. Pinned cross-stack by `micro-workflow-bundle/test/test_units.py::TestUsageTrackingBillsFailedAttempts`, which drives all copies through one synthetic history — a regression here fails the bundle suite, not this stack's.
- **Usage-tracking cost constants** are us-east-1 arm64 figures as of 2025, and billed duration includes ~10–50 ms of Step Functions scheduling latency (small systematic overestimate). `pipeline_wall_sec` is `ExecutionStarted → now`, not `→ ExecutionSucceeded`: that event cannot exist yet while this state is running.
- **`TOKEN_MEL_RATIO = 2` is a hard alignment invariant** — [lib/flow.py](lib/flow.py) asserts `prompt_mel.shape[1] == len(prompt_speech_tokens) * 2`, matching upstream's `frontend_zero_shot` truncation. `<|endofprompt|>` must resolve to id **151646** ([lib/frontend.py](lib/frontend.py) checks and raises).
- **`style` replaces the LLM stage's reference conditioning entirely** — `ref_transcript=""` and `prompt_speech_tokens=[]` are load-bearing in instruct2 mode, not incidental. Voice identity survives via the Flow stage's own conditioning, which is why this is safe (§7a).
- **Every Lambda needs a declared `AWS::Logs::LogGroup`.** A function without one still gets a group — Lambda auto-creates `/aws/lambda/<name>` on first invocation with **never-expire** retention and no stack ownership, so it survives stack deletion and then blocks the next `create-stack` with `already exists`. The validator and `start-build` shipped that way and were caught on a live stack — the `retentionInDays` split is the reliable ownership test: declared groups carry a number, auto-created ones carry `None`. Both custom resources also need a `DependsOn` on their group, or Lambda's first invocation wins the race regardless. `test/test_units.py::TestEveryLambdaHasADeclaredLogGroup` enforces name-for-name coverage, retention, and the two `DependsOn` edges. **`StartBuildLambda` is the exception and is covered separately:** it is deliberately unnamed, so `/aws/lambda/{FunctionName}` is unknowable at author time and it reaches its group through `LoggingConfig.LogGroup` instead — `test_unnamed_functions_route_logs_via_logging_config` pins that, and pins that it is the *only* unnamed function here.
- **DeletionPolicy / table-encryption posture is deliberate.** The DynamoDB tables (voice registry, callback tokens) hold rebuildable derived state and are designed to delete with the stack; default SSE (no customer-managed KMS key) and no PITR are deliberate sample-code posture, recorded in the `checkov` skip comments on each table. Do not "harden" them without deciding the table is no longer disposable.
- **This stack was ported from a separate upstream repo, so its names drifted from the house convention — they were conformed and the divergence must not come back.** `Custom::ProxyBucketValidation` → `Custom::ProxyBucketValidator`, `Custom::BuildAndSeedModels` → `Custom::StartBuildDelayResponse`, `StartBuildFunction` → `StartBuildLambda` (and unnamed, via `LoggingConfig`), `StartBuildLogGroup` → `StartBuildLambdaLogGroup`, `bucket_validator.lambda_handler` → `.handler`. Two of those are **replacements, not in-place edits**, and they fail in different ways: a `Custom::` type rename is safe here (no physical name; `Delete` is a documented no-op that never touches the bucket), but a **log-group logical-id rename that keeps an explicit `LogGroupName` cannot be deployed in one update**. Measured live: CFN replaces create-before-delete, so the new logical id tries to create a `LogGroupName` the old id still owns and the stack dies at *pre-flight* — `Validation failed with 1 error(s)` with **no per-resource event naming the culprit**, then `UPDATE_ROLLBACK_COMPLETE`. A two-step deploy (drop the resource, then re-add under the new id) works, and the old group's contents do not survive (§12 item 12). The logical id `BuildAndSeedModels` deliberately does **not** become the siblings' `StartBuild`: this stack's build also seeds six model archives, so the name is load-bearing.
- **The validator Lambda is `${ResourcePrefix}-tts-bucket-check`** (logical id still `ProxyBucketValidatorFunction`). The old `-tts-proxy-bucket-validator` name was renamed for the sibling workflows' character budget — at prefix 20 the longest sibling equivalent hit exactly the 64-char `FunctionName` limit. Its declared group was renamed to match, which **deleted** the old group: `LogGroupName` is a `createOnlyProperty`, so a rename replaces the resource and CFN drops the old one with its contents. Safe only because it held 0 bytes, checked first. Its role no longer uses `AWSLambdaBasicExecutionRole` — that grants `logs:CreateLogGroup` on every group, which lets a function that can't reach its declared group silently make an unmanaged one; logs are now scoped to the declared group's ARN.
- **CosyVoice3 and faster-whisper are CPU-only here** — do not introduce GPU instance types.

# Design record

The sections below preserve, by number, the design decisions this codebase cites (`§5`, `§7a`, `§10`, …). Measurements quoted here were taken on real deployments — **do not change the pinned values without re-measuring.**

## §0. Phase 1 history (GGUF feasibility build — superseded)

A prior feasibility build (a C++/ggml CLI binary rather than this Python ONNX pipeline) proved CosyVoice3 zero-shot cloning viable on Lambda arm64 at all, and left three lessons carried into this port: the `"You are a helpful assistant.<|endofprompt|>"` chat-template prefix is REQUIRED and easy to miss (omitting it made ~78 % of cloning attempts hallucinate or leak the reference transcript — hence the check in `lib/frontend.py`); the `seed` lever is real (same seed + same inputs → byte-identical output; different seeds change prosody and occasionally rescue a bad clone — the origin of best-of-N); and voice conditioning depends only on reference audio + transcript, never target text — cacheable once, which is the origin of the register/synthesize split (§5). The GGUF build's provenance marking (watermark/C2PA) lived in that binary's C++ layer and was **dropped, not ported** (§12).

## §1. Runtime dependency policy

No PyTorch at runtime, no ffmpeg at runtime — hard constraints. `onnxruntime` and `faster-whisper`+`ctranslate2` are torch-free (verified against their declared dependencies; CTranslate2 is a from-scratch C++ engine, not a torch wrapper). Reference audio must be WAV/PCM16 from the caller — validate, never convert. The bounded time-stretch (§7) is pure NumPy/SciPy DSP, unrelated to ffmpeg.

## §2. Reference implementation & model inventory

Ported from upstream CosyVoice (`class CosyVoice3(CosyVoice2)`; Apache-2.0). Official upstream ships CAMPPlus and speech_tokenizer_v3 as ONNX plus a partial flow export; a community derivative chain provides a complete ONNX export of every component including HiFT and an INT4 LLM. Each community file was independently re-verified (loaded and run, accuracy-gated via ASR roundtrip) rather than trusted. Two findings from that verification shape the model set:

- **The 519 MB `text_embedding` file is a duplicate, not a fourth model** — it is the LLM's own `embed_tokens.weight` split out by the exporter; a future own-export should fold it into the LLM graph rather than ship it.
- **The LLM backbone weights are exported twice** (initial-pass and decode-pass graphs each carry the full ~683 MB backbone); a single graph with optional `past_key_values` would halve the LLM's footprint before any quantization.

The two DSP functions (whisper log-mel, Kaldi fbank) are deterministic transforms reimplemented in NumPy/SciPy, verified numerically against the originals.

## §3. Quantization: size-gated, quality-first — not "quantize everything"

Quantization exists to solve a memory/size problem; applying it to an already-small component is an accuracy cost paid for a saving nobody needed. Decision rule per component: ship FP16/FP32 if it fits the tier; only quantize when the budget genuinely demands it, preferring the least lossy level that fits; and every quantized (or precision-cast) variant must pass the ASR-roundtrip gate **on linux/arm64, the deploy target** — raw tensor MSE says nothing about intelligibility, and macOS passing is not sufficient. Outcomes, all measured:

- **LLM: INT4** — passed the ASR gate, ~3x faster than FP16, and **beat FP16 on a listening comparison** (more natural pitch/tone/prosody). Two concrete contributors: logit perturbation changes the sampled token sequence (some difference is sampling variance), and the INT4 package's decoder/speech-embedding heads are FP32 while the FP16 package's are FP16 — the INT4 path computes its output logits at *higher* precision. This closed the LLM quantization question.
- **Flow estimator: FP32 is final; both quantization paths were tried and rejected on evidence.** INT8 dynamic was 2.1x faster and passed the ASR gate but **failed the listening gate ("very noisy")** — ~0.93 final-mel correlation is audible degradation even when content survives. An own FP16 re-export was accurate (corr 0.998, after repairing a real converter bug — Cast nodes contradicting declared graph types) but **2.3x SLOWER than FP32**: ORT 1.18's CPU EP has no native FP16 kernels, so every op pays cast/compute/cast-back. FP16-on-CPU is a size lever only, never a speed lever, on this stack. The *community* FP16 estimator is numerically broken (correlates only ~0.5 with FP32, platform-dependent through 22 unnormalized DiT blocks, audibly garbled in the Lambda container while passing on macOS). The corrected rule: **depth of unnormalized compute, not file size, predicts cast risk** — "a straight precision cast is safe" is retracted.
- **HiFT: FP32 as-is.** Its 247 MB `[1, 7200000, 9]` Constant is **real, load-bearing model state**, not an export bug — a frozen noise buffer for causal synthesis sized for a 300 s max utterance, confirmed against the upstream source (`SineGen2.sine_waves`). The buffer's values are untrained noise, so an own re-export with a smaller max-duration cap is a verified size opportunity, deferred.
- **speech_tokenizer_v3: FP32** — no quantized ONNX variant exists anywhere, and its discrete FSQ/codebook output makes quantization noise risk a token *flip*, not "slightly off"; any self-quantization attempt gets more scrutiny here, not less.

## §4. Model delivery

Build time: CodeBuild seeds `s3://{ProxyBucket}/_model_artefacts/...` idempotently (`head-object` skip-if-exists). Runtime: `lib/model_store.py`'s `ensure_in_tmp()` (warm-container no-op, atomic staging-dir extraction, path-traversal guard), plus `lib/ort_init.py`'s `ensure_cpuinfo_files()` for the Lambda-arm64 ORT cpuinfo crash (see Gotchas). Model load streams S3 body → gzip → tar in one pass (no intermediate archive in /tmp, constant RAM).

## §5. Voice registry

DynamoDB, modeled on face-recognition's face_store (the house "persistent named entity with derivative artifacts" pattern):

```
pk = "voice#{voice_id}"     sk = "record"
  voice_id, name, gender, language, origin, license, catalog, comment,
  s3_conditioning_key, s3_preview_key, s3_source_key (optional),
  duration_sec, created_at, catalog_created

GSI: catalog-index (catalog, catalog_created)   — list-by-catalog
  catalog_created = "{catalog}#{created_at_ms:015d}", zero-padded-epoch
  composite sort, same pattern as face_store's celeb_created
```

- `license` — the voice's license term, **recorded at registration time, never derived at read time from `origin`** (the origin→license mapping is a fact about the source dataset when it was registered, not a stable rule to re-evaluate later). Defaults: `"IC"` (Individual Contributor — the uploader attests they hold the rights) when `origin == "user-upload"`; the dataset's published license for known baked-in origins (LibriSpeech → `"CC-BY-4.0"`, FLEURS → `"CC-BY-4.0"`); **registration hard-fails for an unknown origin with no explicit license** rather than guessing. Caller can always supply `license` explicitly.
- `origin` — free-form provenance (dataset name, or the literal `"user-upload"`). Does double duty deliberately: `origin == "user-upload"` is the single field splitting the pre-computed catalog-seeding path from the live user-upload path — no separate boolean.
- `language` — needed by §8's whisper QC (must know target language) and catalog filtering; stored normalized (see Key Conventions).
- Three separate S3 keys rather than one prefix, because they have three lifecycles: `s3_conditioning_key` is the ~1 MB blob synthesis actually reads (DynamoDB's 400 KB item limit rules out inline); `s3_preview_key` is a short human-listenable browse clip; `s3_source_key` is the original upload, kept only for `user-upload` as an audit trail.
- **Same schema for baked-in and user-cloned voices** — `origin` distinguishes them; no separate systems.
- Tools: `list_voice_collection` (filter by catalog/gender/language, paginated — mirrors `list_faces`) and `get_voice` (single-voice detail — an agent choosing a voice needs metadata/preview before committing to a synthesis call).
- **Catalog seeding** (§12): the ~46 baked-in FLEURS/LibriSpeech voices ship as one tarball of pre-validated DynamoDB records (already in `BatchWriteItem` wire format) plus a `blobs/` tree mirroring each voice's real S3 keys verbatim, imported by the same CodeBuild that seeds models — **not** re-registered through `register_voice` on every deploy (extraction is deterministic and was already paid for once). The packager filters to known baked-in origins explicitly, so a customer's own uploaded voice can never leak into the shipped bundle.

## §6. Batch transcript synthesis

**One iterator = one voice + a list of transcripts**, and **the transcript loop is inside the Lambda's own Python code** — not a nested Step Functions Map, and not tensor-level batching:

- A flat SFN-level Map (one invocation per transcript, as speech-diarization does) relies on warm-container reuse to amortize model load, which is probabilistic and gets *less* reliable as `MaxConcurrency` rises. A Python loop inside one invocation guarantees the LLM (and cached conditioning) stay loaded across the whole batch.
- Within the loop, sequential per-transcript: the LLM decode is autoregressive and variable-length; padding to tensor-batch wastes compute on CPU with no throughput win, and a plain loop is far easier to reason about. (Not a permanent ban for Flow+HiFT — a testable follow-up if per-call overhead ever dominates.)
- The real cost, paid deliberately: a mid-batch failure needs per-transcript `try/except` recording per-item status, because the SFN `Retry` would otherwise re-run transcripts that already succeeded.
- Assumption flagged: every transcript in one batch shares a `voice_id`. Mixed-voice batches would need the caching model re-checked.
- `transcripts_per_batch` has no tuned default — and it also bounds the LLM→Flow payload directly (§10), so the eventual default is a joint cost/payload decision.

Parallelism comes from the Map's `MaxConcurrency` across iterators (§13a) and ORT's intra-op thread pool (§9).

## §7. Duration control ("speak this in ~10 seconds")

- **Layer 1 — instruct-conditioned duration hint: REJECTED, verified empirically.** Live generations across several numeric targets and seeds showed **zero correlation** between requested and actual duration. Understood via §7a: instruct2 was fine-tuned on a small closed template set; a numeric duration target is fully off-distribution. (Upstream's own `speed` parameter is mel resampling before the vocoder — the same lossy time-stretch, hidden one stage earlier.) Closed, not revisit-pending.
- **Layer 2 — bounded pitch-preserving time-stretch, ±10 % cap** (phase-vocoder, pure NumPy/SciPy). Beyond ±10 %, hard-fail — silently "succeeding" past that threshold produces audibly degraded output (phasiness, transient smearing) while reporting success, which is worse than a clear failure. The ±10 % is provisional; do not raise it without a new explicit decision.
- Explicitly out of scope: rephrasing the caller's text.

## §7a. Style hint (`instruct2` mode) — verified capability, not speculative

**Core finding**: `inference_instruct2` is NOT a general natural-language style engine. CosyVoice3 was fine-tuned on a closed set of exactly **26 fixed instruction templates** (verified against upstream source: 17 Chinese dialect/accent, 2 volume, 2 speed, 3 emotion, 2 role-play). Off-distribution instructions (paraphrases, invented adjectives, atmospheric prose) produce two verified failure patterns: the model reciting fragments of the instruction as spoken content, and high seed-to-seed variance in whether any style lands — corroborated by an upstream GitHub issue reporting the identical bug. On-distribution (verbatim templates), a full sweep across the kept templates and multiple seeds passed the ASR-roundtrip content check with zero instruction-bleeding.

**Mechanism** (verified in upstream frontend source): instruct text goes into the `prompt_text` slot normally holding the reference transcript, and the LLM's reference-audio conditioning is deleted — `ref_transcript=""`, `prompt_speech_tokens=[]` are load-bearing. Voice identity survives via the Flow stage's own conditioning, which is why this is safe.

**Seed is sampling noise, not a style control** — different seeds are different valid "takes", not intensities. A seed sweep found one seed broke multiple off-distribution instructions at once while others held, which had made early single-seed tests look uniformly worse than the templates are. Production default seed is fixed (`style_hints.DEFAULT_SEED = 42`).

**Shipped design** — two tiers over 8 of the 26 templates ([lib/style_hints.py](lib/style_hints.py)):

- **Tier 1 — pace** (`fast`, `slow`): single-shot; the tightest, most reliable effect tested.
- **Tier 2 — emotion** (`happy`, `sad`, `angry`, `cute`, `loud`, `soft`): best-of-3 (`CANDIDATE_SEEDS = (1, 42, 99)`) — higher seed variance than pace. A flat single-parameter group by explicit decision, not semantic uniformity: `loud`/`soft` are physical volume, `cute` is a relabeled children's-cartoon role-play template, folded in as an API simplification.
- Dropped: all 17 Chinese dialect templates (wrong use case for this catalog, not a quality issue) and the "robot" role-play (no natural home in either tier).
- `config.style` is validated fail-fast in `StateCheckAndPreprocess` against `ALL_STYLES`; unknown name → workflow error, never a silent fallback. An explicit caller `seed` forces single-shot even for Tier 2 (best-of-N exists to pick among *unspecified* takes; a caller who names a seed asked for a specific take, not a vote). Verify output QCs every candidate, keeps the highest similarity, deletes the losers' WAVs, and collapses to the flat entry shape — downstream needed zero changes. Live-verified end to end, including that the selection logic genuinely picks non-first candidates and that losing WAVs are actually deleted from S3.
- **Auto-detecting style from transcript content was considered and rejected**: only 3 of the 6 Tier 2 styles are sentiment (volume and role-play should never be driven by transcript emotion), and the same-language path has no LLM call anywhere — auto-detect would add one per request. Open, untested follow-up.

**The language gate (English-only), and the live multilingual test behind it.** All template verification above used English voices. A follow-up multilingual E2E test (5 languages × `fast` + `happy` + unstyled baselines, real FLEURS voices, native-language sentences) found **`fast` causes real content corruption on German and Spanish**: unstyled baselines were clean (QC similarity ~0.95–1.0) on the same voice/text; `fast` dropped them to 0.44–0.67 with genuinely wrong words in the transcription. A regression caused by style mode itself, not pre-existing fragility. Chinese stayed clean under both styles — working hypothesis (unconfirmed): every kept template is Chinese-language instruction text, so Chinese content may be on-distribution in a way other languages are not. `happy` (best-of-3) looked more robust, but one clean run per language is not the verification depth English got. Separately and pre-existing: one Japanese voice/sentence failed QC even unstyled, and one French pair failed baseline but was incidentally rescued by a lucky best-of-3 seed — baseline fragilities on specific pairs, not style regressions. **In response, `StateCheckAndPreprocess` rejects any batch with `config.style` set where the voice's registered `language` is outside `STYLE_VERIFIED_LANGUAGES` (currently `{"en"}`; Chinese deliberately NOT included on one clean data point).** The gate is style-specific — the same non-English voice with no style synthesizes untouched. Deliberately conservative pending the same repeated-verification treatment English got; not a permanent English-only design decision.

**Composition with §7b's dubbing best-of-3 — orthogonal axes, not yet reconciled.** Two independent best-of-3 mechanisms varying different things (text-length-for-duration-fit vs. seed-for-style-cleanliness); naive composition is 9 synthesis calls per line. Proposed default, not decided: dubbing adaptation keeps its own best-of-3 on duration fit, style applied to all 3 candidates at one fixed seed. Flagged so it is not silently decided by whichever code path gets written first.

## §7b. Cross-language dubbing adaptation — research findings, not yet implemented

Professional dubbing is STT → literal translation (reference only) → *adaptation* (rewriting for timing/naturalness) → TTS; literal translation is industry-known to fail timing. This workflow would need an adaptation step **only for cross-language dubbing, never same-language voice swap**. Measured on FLEURS' parallel human-translated corpus (via `test/dubbing_duration_study.py`): literal translation's natural synthesized duration misses the source clip's by more than ±10 % in **72–80 % of cases** across it/de/es/ja. Per-language speaking rates measured there (chars/synthesized-second: it≈13.0, de≈14.8, es≈12.7, ja≈4.2) are the concrete LLM prompt target — nothing else tells an adaptation LLM this pipeline's real rate. Tested two LLM configurations (`test/dubbing_adaptation_study*.py`): model quality alone did not reliably improve duration-fit; **best-of-3 length-varied candidates did**, consistently, across all 4 languages — the same best-of-N pattern §7a reuses. Agreed design, not implemented: adaptation lives *inside* this workflow, gated strictly on `source_language != target_language`; per-call context is the segment + a small neighbor window + a one-time per-speaker style/glossary profile, never the whole transcript resent per call.

## §8. QC gate — vendor the mechanism, not the workflow or the model

Do not invoke speech-diarization as a child workflow and do not duplicate its stack: its pipeline solves a categorically harder problem (unknown speakers, noisy audio). The QC need here is one narrow question on a single-speaker studio-clean synthesized clip: "does this roughly say the requested sentence." So this container vendors `faster-whisper` + `ctranslate2` directly, running **`Systran/faster-whisper-base`** — the bare `base` variant, NOT `base.en`: the two are genuinely distinct repos, and `.en` is an English-only distillation that would silently break all non-English QC (the exact repo id is pinned as a commented constant). `base` (~145 MB) rather than diarization's large model because the job is a coarse correctness check, not maximal transcription accuracy. Loaded via the same `model_store` mechanism as every other model. QC flag-and-returns rather than failing the workflow — see §10.

## §9. Memory-tier variants

The multi-tier pattern is a first-class cost/performance experimentation axis, not convention copied blindly. The original projections (scaled from a prior runtime's RSS ratio) were ~2.5x under for the synthesis states: ORT fully materializes weights into arena memory, the shipped FP16 LLM carried its backbone twice plus the duplicate text-embedding (§2), and **ORT's CPU EP upcasts FP16 weights to FP32 at session-init**, doubling resident size. Measure, don't project. Measured peaks and the routed tiers are in the table in [Lambda Memory Tiers](#lambda-memory-tiers).

Key measured decisions, in order:

- **INT4 LLM adopted** after the FP16 run's wall time was unacceptable: ASR-gated on linux/arm64 first, then confirmed better than FP16 on the listening gate too (§3). The FP16 LLM files were dropped from the model archive.
- **Runtime fixes beat further quantization**: the thread-oversubscription fix (`intra_op_num_threads` derived from memory size — a measured 3× penalty when defaulted; see Gotchas) and streaming model load. Thread-scaling was measured at 3/4/5/6 real CPUs: the estimator stops scaling past ~4 vCPU, so **memory tier is chosen by RAM need, not thread count**.
- **Tier experiment, split by state rather than adopted wholesale**: LLM 2→3 vCPU was ~25 % faster per token but the state is short — absolute saving ~10 s while state cost roughly doubles; poor trade. Flow+HiFT 3→4 vCPU cut cold synthesis ~43 % (7.4→4.2 s per audio-second — bigger than the fixed-shape thread benchmark predicted, because real clips vary and headroom helps HiFT and the allocator) for ~14 % more cost; good trade whenever latency matters. **Decision: keep Flow+HiFT on 7168 MB (4 vCPU); return the LLM to 3584 MB (2 vCPU).** Memory peaks: LLM 2938 MB (vCPU doesn't change RAM need), Flow+HiFT 4998 MB — 7168 has real headroom where 5376 was adequate but tight at 5029 and OOM'd intermittently at 3584 (allocator variance on an identical workload).
- End-to-end, the optimization arc on one fixed 2-clip batch was ~6x faster and ~7x cheaper than the first working deployment, with quality *improved* by the listening gates along the way. Warm-state variance on identical input is essentially zero (within 0.5 s per state); cold-vs-warm (~40–60 s of model download + session init on whichever state lands cold) is the only significant variance source left — a provisioned-concurrency decision for when real traffic exists, not a code question.

## §10. State machine shape

**Synthesis is split into exactly two states — `StateSynthesizeLLM` and `StateSynthesizeFlowHift`.** A three-way split (Flow and HiFT separate) was rejected: Flow's mel output already exceeds the Step Functions **256 KiB** state-payload limit at the shortest clip ever generated, so it would force an S3 round-trip on every call. The two-way split's boundary carries only speech tokens: **~49,000 tokens of headroom** before approaching 256 KiB, against a measured longest clip of 390 tokens (~15.6 s, ~234 chars). Re-derived per-batch once §6 put the loop inside one invocation: what crosses the boundary is the *whole batch's* token arrays, so "whatever default `transcripts_per_batch` gets must be checked against this ceiling, not assumed safe by extrapolation" — which is why `estimate_batch_payload_bytes` and `estimate_map_aggregate_bytes` exist (see Gotchas and §13b). The split also keeps independent memory sizing (§9) and partial retry (a Flow failure never re-runs the LLM decode). The synthesis chain is strictly sequential (each stage consumes the previous stage's real output, verified upstream).

**Register-voice is its own state machine** (two different callers with different trust levels: offline catalog seeding vs. live user upload), with a genuine 3-way Parallel — the three extraction functions independently read the same source at different sample rates and share no mutable state. The register-time transcript check exists because a mismatched reference transcript is not an error upstream — it is **silent, severe corruption of every subsequent synthesis** against that voice (observed directly: word salad, reference-transcript leakage). A fuzzy-match ASR check at registration (threshold 0.70) converts that into an explicit rejection at the moment the user can act.

**QC verdict: flag-and-return — not retry-with-new-seed, not a hard failure.** `StateVerifyOutput` never raises on a QC mismatch; it annotates `outputs[].qc` and the execution stays `SUCCEEDED`. An earlier claim that whisper-base is "measurably non-deterministic across invocations" was **retracted after direct testing**: re-running the full voice catalog repeatedly produced bit-for-bit identical similarity scores every run, and the known-failing clips failed identically every time. The decision stands on corrected grounds: some real clips are legitimately hard for whisper-base (accented pronunciation, numbers, transliteration — reliably mis-heard the same way every time), so a hard gate would block good voices for an ASR ceiling, not a TTS problem; and retry-with-new-seed retries the wrong thing when the failure's source is frequently the ASR side. The visibility gap that decision created was fixed: `batch_qc_summary` (`all_passed`, `passed`, `failed`, `total`, `failed_indices`) on `get_job_status` — informational, not enforced, impossible to miss without deliberately ignoring it.

**Checkpoint/resume** (all three synthesis states): motivating math — at `MAX_TRANSCRIPTS_PER_BATCH = 100` and ~20–24 s per transcript, a full batch is ~2000–2400 s of work in a 900 s Lambda, so **timeout is the expected outcome at the batch size the code allows, not an edge case**. Pattern ported from face-recognition's `StateClusterIdentities` (`LambdaResourceTimeoutException`, same class name deliberately). `lib/checkpoint.py` keys on `{out_prefix}/ephemeral/{state}_checkpoint_{job_id}_{batch_index}.json` — stable across ASL retries, never colliding across batches or states. Before each transcript: remaining time under `REMAINING_TIME_BUFFER_MS` (60 s) → persist progress → raise; the ASL `Retry` (`IntervalSeconds: 2, MaxAttempts: 10, BackoffRate: 1` — resume immediately, not throttling) re-invokes; on re-entry already-done transcripts (success OR per-item error) are skipped. Checkpoints are cleared on every exit path — nothing orphaned on a normal run (verified by S3 listing after a real forced-timeout test). Flow+HiFT never re-synthesizes already-written WAVs on resume: the audio lives under the real `out_prefix`, only the small metadata needs to survive. Residual risk, known and accepted: granularity is per-transcript, so one pathological near-`MAX_TEXT_CHARS` transcript (up to ~20x tokens-per-char) can exceed the budget alone; nothing in real usage approaches it. At real batch sizes the checkpoint mechanism worked but was *slow* — a reference run of 73 short clips spent over half its 52-minute wall clock in timeout overshoot (each cycle burns a full 900 s invocation for ~110–230 s of progress). That is what motivated §13a; checkpoint/resume STAYS regardless, as what makes a mis-sized chunk survivable. Also learned there: **short sentences are not cheap** — per-clip fixed overhead dominates at ~42 chars, so batch heuristics must weigh both a fixed and a per-char term (§13a).

## §10b. Output reshaping — a dedicated `StateCollectResults` (planned, not implemented)

The terminal output nests every result under `data.iterators[].item_data.outputs[]`; every consumer re-implements the same flatten, `item_data` echoes the full input back out (the payload-growth term §13b bounds), and `out_bucket` lives on a different nesting level than the keys it joins with. Decision: a new state between the Map and `Usage tracking` — **not** folded into `StateUsageTracking` (different input contracts: history-derived telemetry vs. payload; different failure semantics: telemetry failure should not destroy the deliverable; and collection must run before tracking). It emits a flat `data.results[]` (global `transcript_index` preserved — per-batch zero-based indices would make `failed_indices` ambiguous; failed entries keep their slot so index *i* always identifies the *i*-th requested transcript) plus `data.results_summary`, as a constructed **whitelist envelope, not a subtraction** (a subtraction silently re-grows when upstream adds a field), dropping `data.iterators`. ASL has no reduce, so a `ResultSelector` cannot do it. Consequences bundled with it: re-derive `estimate_map_aggregate_bytes`; the gateway keeps the nested-shape fallback until no pre-change execution can still be RUNNING; both ASL copies change together.

## §10c. Request-by-reference — `input.request_s3uri` (planned, not implemented)

Accept either an S3 URI or an inline request (exactly one — both present is a rejection, not a merge), persist the inline one to `{out_prefix}/request.json`. **Not a payload fix**: it relieves `StartExecution` and the output echo, but `data.iterators` is built inside `StateCheckAndPreprocess` from whatever was loaded, so the two estimators that actually reject requests are untouched and the effective maximum request size does not change. Real justifications: durable audit trail (execution history expires), replay, and making §10b's dropped echo lossless. Non-obvious constraints recorded: **`$.input` is read-only for the whole execution** (every state reads `event["input"]`, none writes it — resolved request and URI go to `$.data`); the gateway's `workflow_id` must keep hashing request *content*, never the URI (hashing a URI loses idempotency for identical content at two keys, and wrongly reuses an execution when a key's content is overwritten); `request_s3uri` is a hostile-input surface (proxy-bucket-only, parse before boto3); the persist must run after prefix derivation off the *resolved* request and must not be gated on validation success; retries of later states never re-read the request.

## §10d. Returning the losing best-of-N candidates (planned, not implemented)

`config.keep_alternatives: true` (default stays delete) would skip the loser-delete and emit an `alternatives` list ranked by descending similarity, winner excluded — **absent, not empty, when the flag is off** (an empty list would read as "best-of-N found nothing", a different fact from "best-of-1"). This deliberately reverses `verify_output`'s delete-the-losers decision, so it is opt-in: QC similarity measures *intelligibility*, not naturalness, and for the emotion styles that are the only reason best-of-3 exists, the most intelligible take is plausibly not the best-sounding one — a human or agent picking from 3 is the real use case. The storage argument stands as the default: styled requests would otherwise accumulate 3× audio forever with no reader. Constraints: re-derive the aggregate estimator at the keep+emotion+max-transcripts corner; `verify_output` becomes a `config` reader for the first time; and the existing delete already swallows its own failure (a losing WAV can survive today with nothing reporting it) — if alternatives become real, report what survived instead of claiming a deletion that may not have happened.

## §11. AgentCore Gateway tool

The contract surface is documented in [AgentCore Gateway Tool](#agentcore-gateway-tool) above. Decisions behind it:

- Same `{target}___{tool}` convention, flat zip, thin dispatcher as every sibling; `synthesize_speech`/`get_job_status`/`describe_tool` mirror the siblings' patterns, `register_voice` had no precedent, `list_voice_collection`/`get_voice` mirror the face-recognition pair. Output delivery rides the existing `media-outputs___get_download_url` target — no new download mechanism.
- **Dedup asymmetry is deliberate.** Every sibling's `uuid` names the asset it processes, so parameters fully determine output and parameter-hash dedup is right. Synthesis has no single asset: it renders text against a **mutable voice catalog** and (absent an explicit `seed`) samples freshly, so identical parameters do NOT imply an identical result — silently returning an earlier run's audio was the wrong default. Hence `synthesize_speech` generates a uuid4 when the caller supplies no `idempotency_token` (**no token means "do not deduplicate me"**) and folds it into the hash; the token **narrows** dedup rather than replacing the parameter hash (same token + different transcripts still re-runs), and a generated token is not echoed — `workflow_id` already identifies the run. `register_voice` passes **no** token on purpose: `write_voice_record` mints `voice_id = uuid4()` with an unconditional `put_item` and no tool deletes a voice, so a resubmitted identical registration would create a second permanent, unremovable catalog entry — absorbing that retry is worth more than a caller's ability to force a duplicate. **Do not add a token there without first adding dedup at the record layer** (reference ETag + metadata); the prerequisite is also named at the call site.
- **Token plumbing traps.** The token never leaves the gateway: hashed and discarded — not in the execution input, not in any response, not visible to any state (the event `uuid` the states see is the *derived execution name*, because `out_prefix` comes from it and two runs sharing a uuid would overwrite each other's audio). And no poll may read a token back out of an execution: two successive readers existed and were deleted — a re-added reader hands back either the derived id or stale material from an older run, exactly the bug a sibling once shipped and fixed. Regression: a dedicated test block in `test/test_units.py::TestGatewayTool` (fresh-by-default, token idempotency, token-plus-different-params re-running, retired `uuid` rejected on submit, no-echo, token never reaching the state machine, polls returning nothing from either side, `register_voice` staying parameter-only, and the dispatcher's shared warning making no false claim about starting an execution).
- **Duplicate submits return a handle; `ALREADY_RUNNING` was retired, not repaired.** The old answer was a claim about the *run* that nothing had checked (a run that SUCCEEDED hours earlier and one that FAILED both answered `ALREADY_RUNNING`) — it described the gateway's bookkeeping, not the job. The replacement `DescribeExecution`s the run; a brief intermediate behavior that inlined the existing run's full results on the SUCCEEDED branch was **reverted**: a submit could return a per-transcript `outputs[]` its own `OutputSchema` never declared, giving the caller two ways to obtain results with only one checkable. Current behavior on `ExecutionAlreadyExists`: `{"status": <the existing run's>, "job_id", "workflow_id", "message"}` plus `error` on terminal failure — never results. `message` carries the one fact a status cannot: *this call did not resubmit*. The thin shape is also structural: `_start_execution` is shared by two tools across two state machines and has no asset/prefix of its own to echo. No IAM change was needed (`states:DescribeExecution` was already granted on `execution:${ResourcePrefix}-tts*:*`, covering both machines); a `DescribeExecution` failure returns `SFN_DESCRIBE_FAILED` rather than pretending the submit worked. Guarded by `test_already_running_is_gone_from_the_vocabulary` (scans the gateway source with comment bodies stripped) and cross-stack by `micro-workflow-bundle/test/test_units.py::TestSubmitReturnsAHandleNotResults`.
- **Callback-token row format** lives in [gateway_tool/callback_registry.py](gateway_tool/callback_registry.py) — the ONE place the `(execution_arn, token_hash)` key scheme exists, shared by the dispatcher and the callback waker. A separate module deliberately: `gateway_tool/lambda_function.py` is pinned to contain no hashing at all, so the workflow-id hash can never be quietly reimplemented beside its one true home.
- A registration audit against media-toolkit-gateway's template verified tool count, field parity in both directions, `Required` lists, condition wiring (empty-string default gating so omitting the parameter cannot fail the deploy), invoke permissions, and that `media-outputs`' prefix allowlist covers both output WAVs and voice previews with no change. One open question flagged, not a finding: the same prefix makes `voices/{voice_id}/conditioning.npz` presignable, and nothing restricts it to the voice's owner — the allowlist is that stack's shared design.

## §13a. Work-balanced iterator scheduling (deployed and measured — see §13c)

One caller batch → up to `MAP_MAX_CONCURRENCY = 40` contiguous runs in `split_into_iterator_groups`. The fitted cost model is **both** a fixed and a per-char term (`23.42 s + 0.428 s/char` summed across LLM + Flow + QC on the reference run; replaying the run from the per-state coefficients lands within 0.2 % of the measured total) — the fixed cost dominates short clips, the per-char term decides where the cuts go. The split minimizes the heaviest group by bisecting on that value (concurrent iterators mean the Map costs what its slowest iterator costs; a running-average target instead strands a measured 2.2× straggler at the tail). The 900-s-less-buffer ceiling is applied in the same walk, so a group that cannot fit one invocation is split rather than checkpointed — a resume is serial where an iterator is parallel. Order is preserved as a correctness requirement (`transcript_index` is a running counter over iterators in order). On the words question: tokens fit best (R² 0.98) but don't exist until the LLM has decoded; words are the worst of the three candidates (R² 0.83 — a 12-char word costs more than a 3-char one and word count discards exactly that); hence chars (R² 0.87). The trade this knob makes: each iterator re-pays its own cold model loads, so cost rises with iterator count for a much larger wall-clock win (§13c).

## §13b. The aggregate payload ceiling (deployed and measured — see §13c)

Raising `MaxConcurrency` to 40 prompted "should the data move to S3?" — **measured first, and the answer was no: the payload was not large, it was redundant.** Splitting already relieved the per-batch LLM→Flow bound; the binding constraint was the Map's aggregate `ResultPath`, the one bound splitting cannot touch, and it bound purely from each text being stored **three times** (`transcripts[].text`, `qc.expected`, `qc.transcribed`) — 15.9× more than the information required. `verify_output._prune_qc_evidence` now emits one copy: `qc.expected` goes (a byte-for-byte copy of the caller's own input, joined back by `transcript_index`), `qc.transcribed` is kept on failed/errored clips only (the sole non-derivable field and the review pointer for a failure; on a passing clip the threshold guarantees it is a near-copy), and `item["transcripts"]` is popped after the QC loop. Why not S3: (1) it duplicates `lib/checkpoint.py`'s existing mechanism with different failure semantics; (2) ordering becomes a real problem with 40 concurrent writers — a read-modify-write either needs coordination or silently hands clip 40's audio back as clip 3; (3) it would not be the binding constraint anyway (`MAX_TRANSCRIPTS_PER_BATCH` and the 900 s budget bind first). Revisit only if a request legitimately needs >118 transcripts at `MAX_TEXT_CHARS` in one execution — then raise the cap and re-measure before reaching for S3.

## §13c. Measured on deployed code

§13a/§13b's projections were checked by rerunning the reference workload (same 73 transcripts, same voice, same config) against the deployed stack: wall clock fell from 52.2 min to **3.2 min (16.3×, against a projected ~18×)** with **zero** checkpoint resumes, identical clip and QC outcomes, at ~1.6× the cost — decomposed, Flow+HiFT billed-seconds barely grew (the real forward work was unchanged) while LLM billed-seconds grew ~2.6×, which is 34 cold model loads instead of 2. **Cold loads are the entire cost of the parallelism**, so provisioned concurrency or a smaller LLM init is where the next improvement is, not the scheduling. The pruning behaved as designed live: zero iterators carried input `transcripts`, zero entries carried `qc.expected`, `qc.transcribed` survived on exactly the failed clips, and the aggregate ran at ~18 % of the 256 KiB limit. The rerun also caught a real estimator bug the unit tests could not see — the two independently miscalibrated terms that nearly cancelled (detailed in the first Gotcha). Lesson for the next payload change: a synthetic fixture that models the payload more cheaply than production certifies the wrong number; only serializing a real execution's output found this. The same run also exposed the usage-tracking timed-out-invocation bug (fixed; see Gotchas) — cost skewed worse than duration because the dropped invocations were in the largest memory tier.
